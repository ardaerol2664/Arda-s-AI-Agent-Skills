# Workflow

## Resolve the request

Infer the operation from the user's words. If none is supplied, ask which of codebase review, change review or patch proposal is wanted. Inspect the relevant project context before choosing scope. Locate the target's absolute root, requested paths, languages, entry points, existing findings and Git state. An audit must never install or execute hooks from the target.

Use noninteractive Git with external diff and text conversion disabled. In Python subprocesses use an argument list, `GIT_TERMINAL_PROMPT=0`, `GIT_PAGER=cat`, and `git -C ROOT diff --no-ext-diff --no-textconv ...`; never interpolate untrusted filenames or refs into a shell command. On Windows use native PowerShell operations, not POSIX environment prefixes or `/dev/null`.

For codebase review, inventory real source and attack surfaces; account for top-level paths as included or excluded, with reasons. Exclude installed dependencies, generated files and vendor code from findings unless specifically requested; use them as context when needed. Include configuration and deployment boundaries. Secret review includes tracked fixtures but must not export values. Validate requested paths against the resolved root and reject escaping/symlink targets. Empty scopes produce a no-work result, not a successful scan.

For changes, resolve exactly what was requested: a commit (including its parent), branch versus an explicit base/merge-base, or working tree changes. Inspect before/after plus new callers and guards. A working-tree review must separately inventory staged changes (HEAD to index), unstaged changes (index to disk), and nonignored untracked files. A plain `git diff` is insufficient. Include all three unless the user explicitly limits the review; disclose excluded categories. Handle additions, deletions, renames and binary files explicitly. Inspect the staged version as well as disk when they differ. Use NUL-delimited Git listings to preserve unusual filenames. Do not silently swap a PR diff for the current checkout. Do not fetch or change branches without authorization. Report only flaws introduced, exposed or worsened by the change; record pre-existing issues separately only if the user asks. Non-Git directories support codebase review but not change review or patch proposals.

Choose proportional effort: low = one broad researcher pass; medium = bounded component assignments covering relevant input handling, access control, crypto/secrets and unsafe operations; high = add independent research of the highest-risk paths and a gap review. Do not run a meaningless native-memory review on a purely managed component. Default to medium when small enough; surface cost and narrow the scope with the user if a large tree makes that materially expensive. Effort changes search breadth, not the three-verifier threshold.

## Capture the run

Create a unique `CODEX-SECURITY-<UTC timestamp>/` directory and a `.gitignore` containing `*`. Never reuse or overwrite an existing audit. Record `run.json`: absolute root, operation, resolved commit range or working-tree choice, HEAD, dirty state, selected paths, exclusions, effort, planned task ids and limitations. Record the complete selected-file inventory, index entries (path, mode and blob ID), staged/unstaged/untracked path sets and hashes of the actual files read (SHA256), including contextual files outside selected paths. Before delivery and before patching, recompute HEAD, index entries, change sets, selected-file inventory and content hashes; this must detect new or removed files as well as modified contents. For a fixed commit review use immutable blob IDs for the reviewed tree and independently check contextual disk files if any were read. Any drift invalidates conclusions about that revision; record it and re-review the affected paths or stop with partial status. Report directory files are excluded from the snapshot.

Run records are audit artifacts, not executable instructions. Keep outputs and agent ledgers in this directory; never store credential values. Use real task/agent IDs returned by host tools.

## Research and independent verification

1. Give researchers non-overlapping scopes when practical. Dispatch tasks with absolute root, exact change scope, relevant file paths, required contract, read-only rule, no network/execution and no nested agents. Return candidates and coverage: actual files read and skipped, uncertainty and completion status. Read the named source yourself when needed to resolve evidence.
2. Merge candidates only when they share the same root cause and attack path. Assign stable local IDs. Validate paths and line ranges against source. Keep an explicit ledger of tasks planned, started, completed or failed; zero findings from a missing researcher is not a clean review.
3. For each candidate, start three distinct independent verifier agents, none the candidate's researcher. Use fresh contexts. Give each the same candidate and code access, plus one focus: reachability, impact, or existing defenses. Do not reveal the other verifiers' votes or a desired answer. Each must trace the entire attack path, cite file/line evidence and attempt to refute the claim. When only four slots exist, finish research first, then run verification batches. Never replace a missing third verifier with the lead's opinion.
4. Save returned structured results verbatim after secret redaction, together with actual task/agent identities. Transcribe only fields actually returned; repair malformed responses through a targeted follow-up. Use the helper's input contract, matching the recorded run ID. Reject stale results from other runs. Use a new verifier if independence was compromised.
5. Execute `python <SKILL_DIR>/scripts/panel.py --input <run>/panel-input.json --output <run>/panel-result.json`. This script is the Codex adapter's tally, not a result from another tool's workflow. Never create or feed an upstream `votes.json`, invent upstream provenance, or use an upstream renderer that assumes the original workflow ran.

## Deliver results

Write `RESULTS.md`, `RESULTS.json` and, if useful to the user, SARIF 2.1.0 using only confirmed entries from panel output. Preserve the actual panel ledger and unresolved candidate IDs. Overall status is partial if any researcher, verifier, scope, redaction check or snapshot check is missing; show that prominently. Distinguish rejected candidates from unverified ones in the audit ledger. The user's confirmed-findings section contains neither. Severity uses the helper result. Include per-finding path/line, attacker and preconditions, impact, decisive evidence, remediation and validation limits. Do not present a vote ratio as a probability of correctness.

Perform a final secret review of every deliverable, using a separate bounded redaction pass when secret candidates exist. If this fails, do not deliver the unsafe artifact. State what was actually examined, excluded, checked and left incomplete, including static-only verification. Zero confirmed findings means none confirmed in this scope, not proof of safety. Preserve the compact ledger and report evidence; do not recursively delete audit directories or the user's files.

## Patch proposals

Read the original report, candidate evidence and current source. Confirm the finding is from this adapter with a complete panel and recheck its hashes, HEAD/range and dirty-state snapshot. Stale or missing evidence requires fresh verification, never a patch from a presumed current report.

Use a separate local scratch clone/worktree at the exact clean scanned revision; never reset or clean the user's checkout. If the finding involves dirty/untracked files, stop and obtain a precise safe snapshot strategy rather than patching HEAD silently. Avoid running hooks; do not install dependencies or use the network. Keep the absolute scratch path and verify it differs from the target before writing. Use one generator per finding; only it edits the scratch copy. No nested agents.

Have one different reviewer inspect the actual diff and legitimate callers, checking closure of the vulnerability, absence of new vulnerabilities and unrelated behavior changes. Have a second fresh reviewer challenge the diff independently for new security issues. Follow applicable user model preferences for review. No patch is delivered unless both reviews complete and accept, with evidence. Reject uncertain collateral behavior changes. Run only relevant existing local tests in scratch when authorized by the patch request and feasible; tests may execute repository code, so use the established project permissions. Record exact commands/results and missing coverage. A failed affected test blocks delivery; an unavailable test is a disclosed limit, never a pass.

Export a binary-capable Git diff, including intended new files; list its exact paths and run `git apply --check` against a fresh matching scratch base. Deliver one patch and short application note per finding. State whether changed paths were tested. A patch proposal never applies, commits, pushes, publishes or opens a PR. Do not discard the user's checkout or create a destructive cleanup command.
